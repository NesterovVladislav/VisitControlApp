# PWA для iOS: что нужно, чтобы приложение работало с экрана «Домой» без App Store

13.10.2026, обновлено 14.10.2026 · Darya Nesterova

**Статус: PWA опубликовано на https://app.dobrovhod.ru, на реальном iPhone ещё не проверялось (14.10.2026).** PWA вместо App Store, для родителей и для сотрудников, сразу с разблокировкой по Face ID — решено 14.10.2026. Как выкладывать, устанавливать и проверять — раздел «Инструкция» ниже. Что сделано в коде и чего нет — «Код» и «Не сделано». Веб-сборка проверена в Chrome на компьютере: вход, диалоги, кнопка «Обновить», Face ID на виртуальном датчике, фотографии. Сведения о том, что умеет Safari, взяты из документации — такие места помечены «проверить на устройстве».

PWA (Progressive Web App) — это сайт, который пользователь добавляет на экран «Домой» и открывает как приложение: со своей иконкой, без адресной строки. На iOS это единственный способ дать приложение пользователям iPhone без учётной записи разработчика Apple, проверки в App Store и сборки на Mac.

Приложение написано на Expo и React Native. Веб-сборка в проекте была предусмотрена (`react-native-web`, `react-dom`, скрипт `npm run web`), но до 14.10.2026 не использовалась как рабочая: экраны и сервисы писались под телефон и опирались на то, чего в браузере нет. Разделы ниже «Инструкции» — исходная проработка: что пришлось менять и почему.

## Инструкция

### Адреса

| Что | Адрес |
| --- | --- |
| PWA для родителей и сотрудников | `https://app.dobrovhod.ru` |
| API для PWA | `https://app.dobrovhod.ru/api` — тот же домен, сервер пересылает на бэкенд. В сборке API задан путём `/api` без домена |
| API для APK и Expo Go | `https://core.dobrovhod.ru/api` (`eas.json`, `services/api/config.ts`) |
| Политика ПДн | `https://core.dobrovhod.ru/privacy/…`, так же открывается на `app` и `admin` |

Домен PWA не менять: иконка на экране «Домой» и ключи Face ID привязаны к `app.dobrovhod.ru`. После смены домена всем пришлось бы устанавливать приложение заново и снова включать быстрый вход.

### Выкладка новой версии

1. Собрать из ветки, которую выкладываем (сейчас PWA — в `feature/pwa-ios`, поверх неё `codex/native-api-domain`), без локальных `.env`:
   ```bash
   git status                      # без незакоммиченных правок
   npm ci
   npm test && npm run typecheck
   rm -rf dist && EXPO_NO_DOTENV=1 npm run build:web
   ```
   Результат — папка `dist/`: `index.html`, `sw.js`, `manifest.webmanifest`, `icons/`, `_expo/static/…`, `assets/…`.
2. Проверить сборку локально с настоящим API (раздел «Проверка в Chrome на компьютере»):
   ```bash
   npm run serve:web               # http://localhost:8099, API — https://core.dobrovhod.ru/api
   ```
3. Сохранить архив для отката: `tar czf pwa-$(git rev-parse --short HEAD).tar.gz -C dist .` По хэшу в имени файла сборки коммит не определить: на другой машине он получается другим.
4. Скопировать содержимое `dist/` в каталог, который сервер раздаёт для `app.dobrovhod.ru`, **без `--delete`**: старые файлы `_expo/static/…` пусть останутся до следующей выкладки — их ещё может запросить открытое у кого-то приложение.
   ```bash
   rsync -a dist/ <сервер>:<каталог PWA>/
   ```
   Каталог и способ копирования задаёт настройка сервера — она ведётся отдельно от этого репозитория (вопрос 4 в «Открытых вопросах»).
5. Перезапускать ничего не нужно: файлы отдаются как есть.

Что сервер уже делает для PWA и что нельзя сломать при правке его настройки (проверено 14.10.2026):

- любой адрес экрана (`/children`, `/profile/edit`) отдаёт `index.html` — иначе обновление страницы даст 404;
- `index.html`, `sw.js`, `manifest.webmanifest`, иконки — `Cache-Control: no-cache`: по ним телефон узнаёт о новой версии;
- `/_expo/static/…` — `public, max-age=31536000, immutable`: в имени файла хэш, содержимое не меняется;
- `/api/…` пересылается на бэкенд (с префиксом `/api` в `X-Forwarded-Prefix` — по описанию настройки; снаружи этот заголовок не виден), `/api` → `/api/` (308);
- `/privacy/…` открывается и на `app.dobrovhod.ru`.

### Проверка после выкладки

```bash
curl -s https://app.dobrovhod.ru/ | grep -o '<title>[^<]*</title>'          # <title>ДоброВход</title>
curl -s -o /dev/null -w '%{http_code}\n' https://app.dobrovhod.ru/children   # 200
curl -s -o /dev/null -w '%{http_code}\n' https://app.dobrovhod.ru/api/user   # 401: без токена закрыто
curl -sI https://app.dobrovhod.ru/sw.js | grep -i cache-control              # no-cache
```

Затем в браузере: открыть `https://app.dobrovhod.ru`, войти, открыть «Мои дети» и профиль, нажать «↻ Обновить», выйти из аккаунта (должен появиться диалог «Выйти из аккаунта?»).

### Как обновление доходит до пользователей

- Новая версия приходит сама при следующем открытии приложения с сетью: страница грузится сначала из сети, а она ссылается на новые файлы сборки.
- Приложение, открытое во время выкладки, работает на старой версии до следующего открытия.
- Без сети приложение открывается сохранённой версией, но ни войти, ни загрузить данные не получится.

### Откат

Вернуть в каталог PWA содержимое архива предыдущей версии из шага 3 выкладки. Пользователи получат её при следующем открытии. Бэкенд, базу и пересборку APK откат PWA не затрагивает.

### Установка на iPhone — памятка для пользователей

Текст, который можно отправить родителям и сотрудникам вместе со ссылкой:

> **ДоброВход на iPhone**
>
> 1. Откройте ссылку **https://app.dobrovhod.ru** в Safari. Если ссылка открылась в Telegram, WhatsApp или почте — нажмите «Открыть в Safari» (⋯ или значок компаса).
> 2. Нажмите «Поделиться» — квадрат со стрелкой вверх внизу экрана.
> 3. Пролистайте вниз, выберите «На экран „Домой“» и нажмите «Добавить».
> 4. Дальше открывайте ДоброВход с иконки на экране «Домой», а не из Safari.
> 5. Войдите по email и паролю. Приложение предложит быстрый вход — нажмите «Включить» и подтвердите Face ID или Touch ID. Если iPhone попросит сохранить ключ входа — согласитесь.
>
> Пароль понадобится снова, когда закончится срок входа, а также если вы выйдете из аккаунта или удалите иконку.

Ту же инструкцию приложение показывает на экране входа — только на iPhone и iPad в браузере; в установленном приложении её нет. QR-код со ссылкой для стенда в саду можно сделать из того же адреса.

Что важно знать отвечающему на вопросы пользователей:

- **Снова просит пароль, хотя быстрый вход включён.** Вход действует, пока не истёк токен: срок задаёт сервер (`JWT_TTL_MS`, по умолчанию час с момента ввода пароля), продления нет. Face ID открывает приложение только в пределах этого срока — так же, как в APK.
- **Вошёл в Safari, потом открыл с иконки — снова просит пароль.** Так и должно быть: у приложения с экрана «Домой» своё хранилище, отдельное от Safari.
- **Нет «На экран „Домой“».** Ссылка открыта не в Safari, а внутри другого приложения.
- **Быстрый вход недоступен.** Нужна iOS 18 или новее и включённая Связка ключей iCloud (Настройки → [имя] → iCloud → Пароли и Связка ключей) или другой менеджер паролей. Без этого приложение работает, но пароль нужен при каждом открытии.
- **Удалил иконку** — данные приложения тоже удаляются, установка и вход как в первый раз. Ключ «ДоброВход» в «Паролях» остаётся и при следующем включении быстрого входа используется снова.
- **Не открывал приложение долго** — iOS может очистить его хранилище, понадобится войти заново.
- **Скриншоты не запрещены**, в отличие от APK: браузер этого не умеет.
- **Служебные iPhone сада** — иконку можно поставить без ручных шагов, конфигурационным профилем с ярлыком (Web Clip) или через систему управления устройствами.

## Главный вывод

PWA для iOS сделать можно, но это не «включить веб-сборку», а отдельная доработка в три части:

1. **Инфраструктура.** Нужны домен и HTTPS: без них на iOS не работают ни установка на экран «Домой» как приложения, ни камера, ни Face ID через WebAuthn. Сделано: `https://app.dobrovhod.ru` (14.10.2026).
2. **Защита сессии.** Нативные модули биометрии и Keychain в браузере не работают, но у браузера есть свой API: Face ID вызывается через WebAuthn, а токен можно хранить зашифрованным ключом, который выдаётся только после Face ID. Это новый код, но без доработки бэкенда. Запрет скриншотов в браузере невозможен.
3. **Экраны.** Около сорока диалогов (`Alert.alert`) в браузере не показываются вовсе, обновление «потянуть вниз» не работает, сканер QR и клавиатура ведут себя иначе.

Переносятся обе части — родительская и рабочий режим сотрудника (решено 14.10.2026). Родительская (отметить приход и уход, посмотреть детей, профиль) переносится проще. Рабочий режим со сканером QR — сложнее и рискованнее.

## Что iOS даёт и чего не даёт PWA

| Возможность | В PWA на iOS | Что это значит для нас |
| --- | --- | --- |
| Установка | только вручную: Safari → «Поделиться» → «На экран Домой». Системной подсказки «Установить» нет | нужна своя инструкция с картинками на экране входа |
| Запуск без адресной строки | да, если в манифесте `display: standalone` | выглядит как приложение |
| Камера (`getUserMedia`) | да, только по HTTPS; в установленном PWA — с iOS 13.4 | сканер QR возможен: в `expo-camera` уже есть веб-распознавание QR. Проверить на устройстве |
| Выбор фото из галереи и съёмка | да, через системный выбор файла | фотографии в профиле возможны; системной обрезки до квадрата нет |
| Защищённое хранилище (Keychain) | нет | замена — шифрование токена ключом, который выдаёт Face ID (WebAuthn PRF), см. «Защита сессии» |
| Face ID / Touch ID | да, через WebAuthn (`navigator.credentials`). Ответ — не «да/нет», а подпись или секрет от ключа на устройстве | разблокировка по Face ID возможна без бэкенда (PRF, по документации с iOS 18 — проверить на устройстве); вход по passkey — с доработкой бэкенда |
| Запрет скриншотов и записи экрана | нет | на экранах персональные данные детей — риск остаётся |
| Скрытие содержимого в переключателе приложений | ненадёжно: снимок экрана система делает сама | защитный экран при сворачивании гарантировать нельзя |
| Яркость экрана на максимум | нет | QR-код ребёнка будет на обычной яркости |
| Не гасить экран (Wake Lock) | с iOS 16.4; в установленном PWA работало с ошибками до iOS 18.4 | проверить на устройстве |
| Вибрация | нет | отклик на нажатия вкладок пропадёт |
| Push-уведомления | с iOS 16.4, только для установленного PWA и после разрешения | сейчас в приложении пушей нет, на перенос не влияет |
| Работа в фоне | нет: свёрнутое приложение останавливается | опрос очереди отметок идёт только при открытом приложении — как и сейчас |
| Хранилище | своё, отдельное от Safari; может быть очищено системой | настройки и «сад последнего входа» могут пропадать |
| Обновление приложения | через service worker, без магазина | новая версия доезжает сама, но нужна своя схема обновления |

Android PWA тоже работает и ограничений там меньше, но у Android уже есть APK. В документе — только iOS.

## Что нужно сделать

### 1. Домен и HTTPS

- **Домен.** PWA привязывается к адресу: иконка на экране «Домой» ведёт на него. Сменить адрес потом — значит попросить всех установить заново.
- **HTTPS.** Service worker, камера и WebAuthn работают только в защищённом контексте. WebAuthn к тому же привязывает ключ к домену: по IP-адресу Face ID не заработает, а смена домена сбросит ключи у всех. В `deploy/Caddyfile` сейчас только порт 80; для веб-админки сертификат уже выпускается через Certbot (контейнер `visit-control-admin-tls`) — тот же механизм подойдёт.
- **API на том же адресе.** Страница по HTTPS не может ходить к API по HTTP: браузер такие запросы блокирует. Проще всего раздавать PWA с того же Caddy: `/` — приложение, `/api` — бэкенд. Тогда не нужны и настройки CORS.
- **Раздача файлов.** Ещё один блок в `Caddyfile` и каталог со сборкой; для адресов экранов — отдача `index.html`, иначе обновление страницы на любом экране, кроме первого, даст 404.

Это единственная часть, которую стоит сделать в любом случае: HTTPS нужен и для production-сборки APK (`docs/backend-integration.md`).

### 2. Сборка и оболочка PWA

- **Режим сборки.** Сейчас `"output": "static"` — страницы готовятся заранее на сервере сборки. Для приложения, где всё за входом, проще одностраничный режим (`"single"`). Нужно проверить, что сборка `npx expo export --platform web` вообще проходит: веб-сборку давно не запускали.
- **Манифест** (`manifest.json`): название, иконки, `display: standalone`, цвета, стартовый адрес.
- **Теги для iOS.** Safari берёт часть настроек не из манифеста: иконка `apple-touch-icon`, заставки `apple-touch-startup-image` под размеры экранов, стиль статус-бара, `viewport-fit=cover` для вырезов экрана.
- **Service worker.** Кэширует оболочку приложения, чтобы оно открывалось мгновенно и показывало внятный экран без сети. Данные API не кэшируем: на них персональные данные и актуальность важнее.
- **Обновление.** Правило, когда новая версия заменяет старую: при следующем запуске или с подсказкой «Доступна новая версия». Без этого у части пользователей неделями будет старая версия.
- **Инструкция по установке.** На экране входа в Safari — «Нажмите „Поделиться“ → „На экран Домой“». В установленном приложении инструкция не показывается.

### 3. Защита сессии

Сейчас (`docs/pin-biometric-session.md`): токен лежит в Keychain, приложение открывается по PIN или биометрии, скриншоты запрещены, при сворачивании — защитный экран. Нативные модули для этого в браузере не работают: веб-версия `expo-local-authentication` — заглушка (`hasHardwareAsync()` всегда `false`), веб-версия `expo-secure-store` пустая. Но у браузера есть свои API, которыми часть набора заменяется.

| Что есть сейчас | Модуль | В PWA |
| --- | --- | --- |
| Токен в Keychain | `expo-secure-store` | модуля для веба нет. Замена — токен в хранилище браузера, зашифрованный ключом из WebAuthn PRF (см. ниже). Без PRF — только память страницы |
| PIN из четырёх цифр | `services/auth/pin-crypto.ts` | технически возможен, но защищает слабо: без Keychain токен рядом с PIN можно подобрать перебором десяти тысяч вариантов |
| Биометрия | `expo-local-authentication` | модуля для веба нет. Замена — WebAuthn: свой код, бэкенд не нужен (см. ниже) |
| Запрет скриншотов | `expo-screen-capture` | невозможно |
| Защитный экран при сворачивании | `PrivacyShield` | можно скрывать содержимое по событию сворачивания, но гарантии нет |

**Как работает Face ID в браузере.** API — WebAuthn (`navigator.credentials.create` и `navigator.credentials.get`). Приложение один раз создаёт ключ на устройстве (passkey), дальше каждый вызов требует Face ID или Touch ID. В отличие от нативного модуля, ответ — не «прошёл / не прошёл», а подпись или секрет от этого ключа. Отсюда два способа использования:

1. **Локальная разблокировка, без бэкенда.** Расширение PRF после Face ID выдаёт секрет, постоянный для этого ключа. Из него получается ключ шифрования (WebCrypto), им шифруется токен в хранилище браузера. Без Face ID токен не расшифровать — по смыслу то же, что сейчас делает Keychain с биометрией. PRF в Safari есть, по документации, с iOS 18 — проверить на устройстве.
2. **Вход по passkey, с доработкой бэкенда.** Подпись проверяет сервер, и вход вообще без пароля. Нужно, если требуется заменить сам вход по паролю, а не только разблокировку.

Просто вызвать Face ID и поверить результату в JS (без PRF и без сервера) можно, но это не защита: токен при этом лежит рядом в открытом виде.

Ограничения WebAuthn на iOS:

- нужен домен и HTTPS: к IP-адресу ключ не привязывается;
- при создании ключа пользователь видит системный диалог «Сохранить ключ входа»; нужна включённая Связка ключей iCloud или другой менеджер паролей;
- Safari разрешает вызов только по нажатию: при запуске нужна кнопка «Разблокировать по Face ID», автоматически окно не появится;
- если хранилище браузера очищено системой, зашифрованный токен пропадает — вход по паролю, как после истечения токена.

Токен живёт один час, продления нет: и сейчас через час приложение просит email и пароль заново. Значит, Face ID и в APK, и в PWA избавляет от пароля только в пределах этого часа.

**Решение (14.10.2026): сразу с разблокировкой по Face ID через PRF**, без доработки бэкенда:

- после входа по паролю приложение предлагает включить Face ID — как сейчас в APK (`biometric-setup-screen`): создаётся ключ, токен шифруется и сохраняется в хранилище браузера;
- при следующем открытии — кнопка «Разблокировать по Face ID», токен расшифровывается;
- если PRF не поддерживается (iOS старше 18, нет Связки ключей iCloud или менеджера паролей) или пользователь отказался — токен только в памяти страницы: закрыл приложение или прошёл час — вход по email и паролю (менеджер паролей iOS подставит их сам);
- PIN в PWA не делаем: без Keychain он почти ничего не защищает.

Вход по passkey и сессия в защищённой cookie, недоступной скриптам, — только если понадобится отказаться от пароля совсем или продлевать сессию дольше часа: сейчас бэкенд выдаёт только JWT по паролю.

Запрет скриншотов не заменить ничем. Это нужно принять как ограничение и, возможно, отразить в политике ПДн.

- **Тема оформления, «сад последнего входа»** — хранятся в хранилище браузера, работают.

### 5. Проверка

Автотесты проверяют логику, а не браузер. Нужна проверка руками на реальных iPhone: минимум две версии iOS (текущая и предыдущая), с вырезом экрана и без. Симулятор iOS есть только на Mac.

## Что не переносится

- запрет скриншотов и записи экрана;
- хранение токена в Keychain (замена — шифрование через WebAuthn PRF, см. «Защита сессии»);
- код биометрии как есть: нужен свой на WebAuthn;
- максимальная яркость на экране QR-кода;
- вибрация;
- системный жест «назад».

## Этапы

1. **Домен, HTTPS, раздача сборки.** Сделано: `https://app.dobrovhod.ru` (14.10.2026).
2. **Проверка на реальном iPhone** — таблица «Первая проверка на реальном iPhone» в «Инструкции»: камера и распознавание QR в установленном PWA, Face ID через WebAuthn и поддержка PRF, клавиатура в шторках, удержание экрана. Один-два дня. Рабочий режим делаем в любом случае; если что-то не работает — ищем обход до этапа 4.
3. **Родительская часть.** Вход с разблокировкой по Face ID (PRF), замена диалогов и обновления списков, манифест, service worker, инструкция по установке. Экраны: вход, регистрация, «Мои дети», профиль, группа ребёнка.
4. **Рабочий режим:** «Посещение», «Заявки», «Сад», «Люди», сканер QR.
5. **По необходимости:** вход по passkey и cookie-сессия (с бэкендом); push-уведомления.

Главный объём — этап 3: замена диалогов затрагивает почти все экраны, и после неё нужно перепроверить и APK, потому что код общий (см. «Что это значит для APK»).

## Что это значит для APK

Код у APK и PWA один, а правки для PWA затрагивают почти все экраны. Сломать Android можно, но это зависит от того, как делать правки.

### Что Android не затрагивает

- Домен, раздача сборки в Caddy, манифест, service worker, раздел `web` в `app.json` — Android-сборка их не использует.
- Файлы с суффиксом `.web.ts` / `.web.tsx`. Сборщик подставляет их только в веб-сборку, Android берёт обычный `.ts`. Так стоит делать всё, что в браузере устроено иначе: хранение токена, Face ID через WebAuthn, загрузку аватаров. Например, рядом с `services/auth/biometrics.ts` — `biometrics.web.ts`.
- Ветки `Platform.OS === 'web'`.
- Библиотеки на JavaScript только для веба. Новых нативных модулей PWA не требует, поэтому пересобирать APK из-за зависимостей не придётся.

### Что меняет и Android

| Правка | Риск | Как делать |
| --- | --- | --- |
| Замена `Alert.alert` (42 вызова в 18 файлах) | главный. Если везде поставить свой диалог, на Android поменяются вид и поведение всех диалогов | обёртка: на телефоне вызывает тот же `Alert.alert`, в браузере показывает свой диалог. Но правка всё равно проходит по 18 файлам — можно перепутать порядок кнопок, стиль «Отмена», обработчик. Каждый диалог проверить на Android |
| Кнопка «Обновить» вместо «потянуть вниз» | меняет Android, если показывать её всем | показывать только в вебе |
| Сессия и вход (`store/sagas/auth.ts`, `services/auth/protected-session.ts`) | логика общая: ошибка в ветвлении «в браузере токен в памяти, на телефоне — в Keychain» ломает вход на Android | различия прятать в модулях хранения (`.web.ts`), саги не трогать |
| Клавиатура и отступы | правка без развилки по платформе меняет вёрстку и на Android | только внутри `Platform.OS === 'web'` или в `.web.tsx` |

### Как не сломать

- Различия держать в `.web.*` файлах и обёртках, общие экраны менять минимально.
- После каждого этапа собирать `preview` APK и проходить основные сценарии на Android.
- `npm test` после каждой правки. Тесты проверяют поведение на телефоне, поэтому регрессии в логике поймают, но вёрстку и диалоги — нет. Тесты для веб-сборки нужно добавить отдельно.

## Проверка в Chrome на компьютере

Два способа.

**Разработка: `npm run web`** — `http://localhost:8081`, правки видны сразу, API — `https://core.dobrovhod.ru/api` (адрес по умолчанию в `services/api/config.ts`). Страница с `localhost` ходит на другой адрес, поэтому на сервере должен быть включён CORS для `http://localhost:8081` (`CORS_ALLOWED_ORIGINS`, бэкенд, `deploy/DEPLOY.md`, «CORS для разработки PWA»). Код CORS на сервере есть, но на 14.10.2026 переменная не задана — без неё вход падает с ошибкой сети. Это режим разработки, а не итоговая сборка: service worker не регистрируется, адреса API другие.

**Как будет на сервере: сборка + `serve:web`.** Перед выкладкой и для проверки PWA целиком — та же сборка, что поедет на сервер, и локальный сервер, который, как сервер `app.dobrovhod.ru`, пересылает `/api` на `https://core.dobrovhod.ru/api`. CORS здесь не нужен: страница и API на одном адресе.

```
npm run build:web
npm run serve:web     # http://localhost:8099
```

Другой бэкенд или порт: `API_TARGET=http://localhost:8080 PORT=3000 npm run serve:web` (локальный бэкенд — без `/api` в адресе). После правок в коде — снова `build:web`.

Общее для обоих способов:

- **Вид iPhone:** DevTools → Toggle device toolbar → iPhone. Тогда на экране входа появляется инструкция по установке.
- **Face ID:** на компьютере без датчика быстрый вход не предлагается — приложение после входа открывается сразу. Чтобы проверить путь с Face ID: DevTools → ⋮ → More tools → WebAuthn → Enable virtual authenticator environment → добавить датчик: protocol `ctap2`, transport `internal`, Supports resident keys и Supports user verification. Если у датчика нет поддержки PRF, приложение покажет «На этом устройстве быстрый вход недоступен» — это тоже проверка, но не основного пути. Включённая галочка Supports user verification означает «Face ID пройден».
- **Сохранённый токен:** DevTools → Application → Local Storage → `visit-control.web-session.v1` — только зашифрованный.
- **Начать с нуля:** Application → Storage → Clear site data.

## Код

Всё, что в браузере устроено иначе, — в файлах `.web.ts` / `.web.tsx`: сборщик берёт их только в веб-сборку, Android их не видит. Общий код тронут в нескольких местах, перечислены ниже.

**Оболочка PWA** (только веб):

- `public/index.html` — шаблон страницы: манифест, `apple-touch-icon`, `viewport-fit=cover`, цвет статус-бара, регистрация service worker (только по HTTPS).
- `public/manifest.webmanifest`, `public/icons/` — название, `display: standalone`, иконки 180, 192 и 512 из `assets/images/icon.png`.
- `public/sw.js` — service worker. Страница — сначала из сети, без сети — сохранённая копия; файлы сборки — из кэша; `/api` не трогает. Новая версия приходит сама при следующем запуске с сетью.
- `app.json` → `web`: `output: single` (одна страница вместо заранее отрисованных), `lang: ru`, название.
- `npm run build:web` — сборка с API по пути `/api`. `npm run serve:web` (`scripts/serve-web.js`) — локальная раздача сборки с пересылкой `/api`.
- Название «ДоброВход» и иконка «ДВ»: `app.json`, `public/manifest.webmanifest`, `public/index.html`; иконки рисует `scripts/brand/generate-icons.js`.

**Сессия и Face ID:**

- `services/auth/web-session-vault.ts` — WebAuthn + PRF: создание ключа входа, секрет после Face ID, шифрование токена AES-GCM в `localStorage`. Ключ устройства запоминается и при следующем входе используется снова — в «Паролях» не копятся одинаковые «ДоброВход». Если Safari не выдал секрет при создании ключа, повторное нажатие «Включить» берёт уже созданный ключ.
- `services/auth/web-session.ts` — токен в памяти страницы и связь с хранилищем.
- `protected-session.web.ts`, `biometrics.web.ts`, `session-policy.web.ts` — браузерные версии модулей сессии с тем же интерфейсом.
- `components/session/biometric-setup-screen.web.tsx` — «Быстрый вход» сразу после входа, с объяснением, если Face ID не включился.
- `components/session/unlock-screen.web.tsx` — «Разблокировать» (Face ID только по нажатию) и «Войти по email и паролю»; без Face ID после долгого сворачивания — «Сессия закрыта».
- `services/auth/screen-privacy.web.ts` — без него браузер навсегда закрывал приложение защитной заставкой: запрет скриншотов там недоступен, и ошибка считалась «защита не включилась».

**Экраны** (только веб):

- `components/web-alert-host.web.tsx`, `services/ui/web-alert-queue.ts` — свой диалог вместо `Alert.alert`. Подмена при загрузке страницы, экраны не тронуты: все 42 вызова работают как есть. Порядок кнопок как в iOS, по одному диалогу за раз, поверх шторок.

- `services/photos/photo-form.web.ts` — отправка фотографии: браузерный FormData не понимает `{ uri }`, файл сначала читается.
- `components/install-hint.web.tsx` — инструкция по установке на экране входа: только на iPhone и iPad в браузере.

**Общий код — что изменилось и для Android:**

- `store/sagas/auth.ts` — ветки по `usesPinLock`: на телефоне `true`, путь с PIN прежний. В браузере после входа — предложение Face ID или сразу проверка сессии; ошибки включения Face ID не роняют сессию; тексты ошибок без упоминания PIN.
- `store/reducers/auth.ts` — действия `biometricOfferRequired` и `biometricEnrollmentFailed`, на телефоне не вызываются.
- `services/api/config.ts` — путь `/api` без домена принимается только в браузере; на телефоне по-прежнему нужен HTTPS-адрес.
- `services/api/visit-control-api.ts` — форма с фотографией вынесена в `services/photos/photo-form.ts`, стала асинхронной; содержимое для телефона то же.
