# Защищённая сессия: PIN и биометрия

## Что изменилось

После успешного входа приложение один раз просит создать PIN из четырёх цифр и предлагает включить биометрию. JWT сохраняется только в системном защищённом хранилище (iOS Keychain / Android Keystore), а PIN сохраняется как солёный SHA-256 verifier — не открытым текстом.

Полный логин по email и паролю нужен снова, если сервер отклонил токен, пользователь вышел из аккаунта, защищённое хранилище было очищено или PIN пять раз введён неверно.

## Состояния приложения

1. При первом входе: email и пароль → создание и подтверждение PIN → предложение биометрии → проверка токена через `GET /user` → «Мои дети».
2. При холодном запуске сохранённая сессия всегда открывается в заблокированном состоянии. Для разблокировки нужен PIN или включённая ранее биометрия.
3. После успешной локальной разблокировки приложение отправляет сохранённый JWT в `GET /user`. Только успешный ответ открывает защищённые экраны.
4. При сетевой ошибке, таймауте или `5xx` сессия не удаляется: показывается повтор проверки.
5. При `401` сессия удаляется и показывается обычный вход.
6. При ошибке Keychain/Keystore приложение закрывает доступ к данным и предлагает повторить обращение к хранилищу.

## Правила безопасности

- Бэкенд выдаёт JWT на один час (`3 600 000` мс), refresh-токена нет.
- Клиент не доверяет локальному декодированию `exp`: актуальность подтверждают `GET /user` и `401` от защищённых методов.
- После пяти неверных попыток PIN локальная сессия удаляется. Следующий вход выполняется по email и паролю.
- Успешная биометрия сбрасывает счётчик неверных PIN.
- На Android допускается только сильная биометрия (`BIOMETRIC_STRONG`). Системный PIN/графический ключ не заменяет PIN приложения.
- При сворачивании содержимое скрывается защитным экраном; для защищённой сессии также включена нативная защита снимков экрана.
- Установка приложения заново очищает возможный оставшийся защищённый сеанс этой установки.

## Правило пяти минут

- Возврат в приложение раньше чем через 5 минут не требует PIN повторно.
- Возврат через 5 минут или позже переводит сессию в заблокированное состояние.
- Холодный запуск блокирует сессию независимо от длительности отсутствия.
- Таймаут сверяется по монотонному и календарному времени: перевод часов назад не продлевает окно, а глубокий сон Android не исключается из пяти минут.

## Биометрия и запасной сценарий

- Биометрия включается только по явному согласию после создания PIN.
- Если датчика нет, биометрия не настроена, временно заблокирована или пользователь отменил диалог, всегда остаётся вход по PIN приложения.
- Face ID нельзя полноценно проверить в Expo Go на iOS. Нужна development/release-сборка с подключённым `expo-local-authentication` и описанием Face ID из `app.json`.

## Локальный запуск и проверки

```bash
npm install
npm run test:ci
npm run typecheck
npm run lint
npx expo-doctor
npm run ios
npm run android
```

Для локальной тестовой release-сборки APK без подключённого устройства:

```bash
EXPO_PUBLIC_API_URL=http://93.77.168.178/api \
EXPO_PUBLIC_ALLOW_INSECURE_HTTP=1 \
  npx expo prebuild --platform android --no-install

EXPO_PUBLIC_API_URL=http://93.77.168.178/api \
EXPO_PUBLIC_ALLOW_INSECURE_HTTP=1 \
  ./android/gradlew -p android assembleRelease \
  -PreactNativeArchitectures=arm64-v8a
```

Нативный каталог `android/` генерируется и не коммитится. Получившийся тестовый APK предназначен для современных arm64-устройств. Те же две переменные нужны для iOS-сборки, которая обращается к тестовому HTTP-стенду.

`EXPO_PUBLIC_ALLOW_INSECURE_HTTP=1` добавляет исключения ATS на iOS и `usesCleartextTraffic=true` на Android только в явно помеченную тестовую сборку. Без флага HTTP заблокирован на обеих платформах. Для production обязательно задайте `EXPO_PUBLIC_API_URL=https://<домен>/api` и не включайте HTTP-флаг: release без HTTPS URL завершится fail-fast вместо отправки учётных данных на неподходящий адрес. Профиль EAS `preview` уже содержит обе тестовые переменные; `production` ожидает HTTPS URL из окружения сборки. Публикация в App Store и Google Play требует HTTPS.

## Ручной чек-лист iOS и Android

- [ ] Войти по тестовому email и паролю.
- [ ] Создать PIN и подтвердить его; несовпадающее подтверждение должно сбросить ввод.
- [ ] Принять или пропустить предложение биометрии.
- [ ] Полностью закрыть и открыть приложение: должен появиться экран разблокировки, без показа детских данных.
- [ ] Разблокировать правильным PIN.
- [ ] Свернуть приложение меньше чем на 5 минут: повторная разблокировка не требуется.
- [ ] Свернуть на 5 минут или дольше: требуется PIN/биометрия.
- [ ] Пять раз ввести неверный PIN: сохранённая сессия удаляется и открывается полный вход.
- [ ] Проверить успешную биометрию, отмену, отсутствие/блокировку биометрии и PIN fallback.
- [ ] Отключить сеть после локальной разблокировки: показывается повтор проверки, сессия не удаляется.
- [ ] Вернуть сеть и повторить проверку: защищённые экраны открываются.
- [ ] Нажать «Выйти из аккаунта»: токен и локальная сессия удаляются.
- [ ] Проверить, что защищённые deep link и жест «назад» не обходят экран PIN.

## Поддержка и диагностика

JWT, пароль и PIN не должны попадать в логи, Redux DevTools, скриншоты или отчёты об ошибках. При диагностике фиксируйте только фазу сессии, HTTP-статус и тип сбоя. Если защищённое хранилище недоступно, не предлагайте обычный вход поверх потенциально неочищенной сессии — сначала восстановите доступ к хранилищу или переустановите тестовое приложение.
