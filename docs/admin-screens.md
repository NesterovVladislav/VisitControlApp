# Экраны администратора

25.09.2026 · Darya Nesterova

После входа пользователь с ролью `ADMIN` попадает в раздел администратора. Там он подтверждает заявки на регистрацию, заводит детей и родителей, связывает их, ведёт филиалы и группы и видит, кто сейчас в саду. Если администратор ещё и родитель, он может переключиться в режим родителя.

**Статус: сделаны каркас, «Посещение» (с выбором филиала и составом групп), «Заявки», «Сад» (`docs/garden-screen.md`); «Люди» — список детей, родителей и сотрудников.** Реализованы вкладки администратора, переключение между режимами администратора и родителя (раздел «Администратор-родитель»), первые версии «Посещения» и «Заявок» на текущем API (см. «Что сделано» в этих разделах). Вкладка «Сад» — филиалы, группы и их состав, «Люди» — список детей, родителей и сотрудников с поиском, во вкладке «Ещё» есть профиль (со сменой пароля), «Режим родителя» и «Выйти». Остальное пока только проработано. API сверено со стендом `http://93.77.168.178/api/v3/api-docs` и кодом `visit-control-service` на 25.09.2026. Примерно половину экранов можно сделать на текущем API. Остальным нужны доработки бэкенда, они собраны в разделе «Что нужно на бэкенде».

## Куда попадает пользователь после входа

Роль приходит в `GET /user` (`role.role`) и уже лежит в `state.auth.user.role`.

Директор (`DIRECTOR`) в приложении работает как администратор: те же вкладки и права (`isAdminRole` в `store/types/auth.ts`).

| Роль | Экран после входа |
| --- | --- |
| `ADMIN`, `DIRECTOR` | режим, в котором он работал в прошлый раз; при первом входе — вкладка «Посещение» (см. «Администратор-родитель») |
| `PARENT` | «Мои дети» (`docs/children-screen.md`) |
| остальные | «Приложение пока работает для родителей и администраторов» и кнопка «Выйти» |

Проверка роли на клиенте только выбирает экраны, настоящая защита — права на бэкенде.

## Администратор-родитель

Администратор сада часто водит в этот же сад своих детей. Утром он приводит ребёнка, отмечает приход и сразу переходит к работе, вечером наоборот. Поэтому у него два режима в одном аккаунте:

- **режим администратора** — вкладки «Посещение», «Заявки», «Сад», «Люди», «Ещё»;
- **режим родителя** — ровно тот же экран «Мои дети», что у обычного родителя (`docs/children-screen.md`), ничего дополнительного.

Режим — только способ показа. Права не меняются: токен тот же, и в режиме родителя бэкенд по-прежнему видит администратора. Разделение нужно, чтобы утренняя отметка своего ребёнка занимала два тапа, а не поиск себя в «Людях», и чтобы родительский экран не смешивался с рабочими списками.

### Когда доступен режим родителя

Переключатель показывается, только если у администратора есть свои дети: после входа приложение в фоне запрашивает `GET /child-representative/children` со своим ключом. Пустой ответ — переключателя нет, и администратор без детей ничего лишнего не видит. Связь создаётся так же, как для любого родителя, в том числе самим администратором из своей карточки в «Людях».

**Сейчас в API:** всё есть. У `ADMIN` все права, включая `CHILD_REPRESENTATIVE_READ` и `VISIT_WRITE`, а `POST /visit` проверяет только наличие связи ребёнка с представителем.

### Как переключаться

```
Режим администратора → «Ещё»          Режим родителя → «⋯» в шапке
┌─────────────────────────────────┐   ┌─────────────────────────────────┐
│  Ещё                            │   │  Мои дети                   ⋯   │
│                                 │   │                                 │
│  ┌───────────────────────────┐  │   │  ┌───────────────────────────┐  │
│  │ 👪 Режим родителя       › │  │   │  │ Мария Иванова             │  │
│  │    Мария, Пётр            │  │   │  │ ○ Не в саду               │  │
│  └───────────────────────────┘  │   │  │ [    Привела в сад    ]   │  │
│                                 │   │  └───────────────────────────┘  │
│  Сменить пароль               › │   │                                 │
│  Выйти                          │   │  ┌───────────────────────────┐  │
│                                 │   │  │ Режим администратора      │  │
│                                 │   │  │ Выйти                     │  │
│                                 │   │  │ Отмена                    │  │
│                                 │   │  └───────────────────────────┘  │
└─────────────────────────────────┘   └─────────────────────────────────┘
```

- **В режим родителя:** первая строка вкладки «Ещё», крупная, с именами детей. Два тапа: «Ещё» → «Режим родителя».
- **Обратно:** «⋯» в шапке «Мои дети» → «Режим администратора». У обычного родителя в этом меню только «Выйти», поэтому пункт появляется лишь при роли `ADMIN` или `DIRECTOR`.
- Переключение без подтверждения и без перезагрузки данных: это не выход из аккаунта, ошибиться тут нечем.
- Отдельную вкладку «Мои дети» в нижней панели не делаем: вкладок уже пять, а шестая станет нечитаемой. К тому же родительский экран внутри рабочих вкладок снова смешает два контекста.

### Какой режим открывается при входе

Приложение запоминает последний режим и открывает его при следующем входе. Утром администратор отметил ребёнка в режиме родителя и не переключился — при следующем открытии он снова в режиме родителя, одно переключение. Если бы всегда открывался режим администратора, отмечать ребёнка пришлось бы через лишний шаг каждый раз.

Если запомнен режим родителя, а детей у администратора больше нет (связи удалили), открывается режим администратора.

Режим хранится на устройстве вместе с сессией: `expo-secure-store` всё равно появится для токена (этап 1 в `backend-integration.md`). Пока сессия живёт только в памяти, режим тоже сбрасывается при перезапуске, и при каждом входе открывается «Посещение».

### Как выглядят отметки администратора

В журнале и в карточке ребёнка отметка администратора-родителя выглядит как у любого родителя: «привела Иванова А.». Отдельной пометки «администратор» не нужно: он действовал как представитель своего ребёнка.

Отметка чужого ребёнка из режима администратора (например, родитель забыл отметить) — другой сценарий, он в открытых вопросах. Если его сделают, в журнале такие отметки нужно помечать «отметил администратор», чтобы родитель не удивлялся, что «привёл» кто-то чужой.

### Что меняется в приложении

| Файл | Изменение |
| --- | --- |
| `store/reducers/auth.ts` | поле `mode: 'admin' \| 'parent'` и action `switchMode`; для `PARENT` всегда `'parent'` |
| `store/sagas/auth.ts` | после входа администратора — фоновая загрузка своих детей, чтобы знать, показывать ли переключатель; при `switchMode` — сохранение режима |
| `app/auth.tsx` | после входа маршрут выбирается по `role` и `mode`, а не только по роли |
| `app/children.tsx` | «Выйти» в шапке заменяется на меню «⋯»: «Режим администратора» (только `ADMIN`) и «Выйти» |
| `app/(admin)/more/index.tsx` | строка «Режим родителя» с именами детей, если дети есть |

Переключение — `router.replace` на `/children` или `/(admin)/visits`. Стеки вкладок администратора при этом сбрасываются, но данные остаются в кэше RTK Query, и при возврате экраны открываются сразу, без спиннера.

Список детей для «Мои дети» и для строки в «Ещё» — один и тот же slice `children`. Загруженный в фоне список сразу виден при переключении.

## Сотрудник

Роль `EMPLOYEE` — воспитатель или другой сотрудник сада с доступом к приложению (с 28.09.2026).

- **Видит весь сад:** рабочий режим с вкладками «Посещение» (кто в саду по филиалам и группам, журнал) и «Ещё» (профиль, режим родителя, выход).
- **Не видит и не может:** «Заявки», «Сад», «Люди» — не создаёт людей, не одобряет заявки на регистрацию, не ведёт филиалы и группы. На бэкенде это закрыто правом `USER_WRITE` (и `BRANCH_WRITE`), которого у сотрудника нет; в приложении эти вкладки скрыты.
- **Может быть родителем в этом саду.** Переключение режимов такое же, как у администратора-родителя (раздел выше): «Ещё» → «Режим родителя», обратно — «⋯» в «Мои дети» → «Режим сотрудника». В токене у человека одна роль, поэтому у `EMPLOYEE` есть и права родителя: `VISIT_WRITE`, `CHILD_REPRESENTATIVE_READ`/`WRITE`. Отметить можно только своего ребёнка: `POST /visit` проверяет связь ребёнка с представителем.
- Права: `PRESENCE_READ`, `VISIT_READ`, `GROUP_READ`, `BRANCH_READ` + родительские. Миграция `2026-09-28-employee-role.xml`.
- **В приложении:** «роль персонала» (`isStaffRole` в `store/types/auth.ts`) — администратор или сотрудник: у них рабочий режим и переключение в режим родителя, свои дети загружаются сразу после входа. Вкладки только для администратора скрыты через `href: null` в `app/(admin)/_layout.tsx`.

## Вкладки

Пять вкладок внизу экрана: больше в нижнюю панель не помещается без сокращений.

| Вкладка | Что внутри | Зачем отдельная вкладка |
| --- | --- | --- |
| **Посещение** | кто сейчас в саду по группам и журнал отметок | самые частые вопросы: сколько детей, кто где, кто кого привёл и забрал |
| **Заявки** | заявки на регистрацию; число ожидающих — на значке вкладки | ежедневная работа, должна быть в один тап |
| **Сад** | филиалы → группы → состав группы | структура сада и работа с группами |
| **Люди** | дети, родители и сотрудники: поиск, создание, карточки | когда нужен конкретный человек, а не группа |
| **Ещё** | мои дети, смена пароля, выход | редкие действия |

```
┌─────────────────────────────────────┐
│                                     │
│            (содержимое)             │
│                                     │
├─────────┬───────┬──────┬──────┬─────┤
│    ◉    │  ✉ 3  │  ⌂   │  👤  │  ⋯  │
│Посещение│Заявки │ Сад  │ Люди │ Ещё │
└───────┴───────┴───────┴──────┴──────┘
```

Внутри каждой вкладки свой стек экранов: из «Сад» можно уйти вглубь до карточки ребёнка, переключиться на «Заявки» и вернуться в «Сад» туда же, где был.

## Посещение

Вверху экрана переключатель из двух частей (`segmented-control`): «Кто в саду» и «Журнал». Вкладка помнит последний выбранный режим.

### Очередь

С 12.10.2026, если в саду включено подтверждение посещений (`visit_confirmation` в `GET /organization/current`), у переключателя появляется третий режим — «Очередь N». В нём отметки родителей «Привела» и «Забрала», которые ждут сотрудника: «Принять», «Отдать» или «Отклонить» с причиной. Сотрудник выбирает свои группы («Изменить»), выбор хранится на устройстве; сколько ждут в остальных группах — строкой под списком. Очередь открывается первой, пока в ней кто-то ждёт, и перечитывается раз в 15 секунд. Свою отметку сотрудник-родитель подтвердить не может.

Полное описание — `visit-control-service/docs/visit-confirmation.md`. Код: `components/visit-queue.tsx`, slice и saga `visit-queue`, `utils/visit-queue.ts`, `services/visits/queue-filter.ts`. «Отметить без телефона родителя» пока не сделано.

В очереди есть кнопка «Сканировать QR-код родителя» (`components/qr-scanner-sheet.tsx`, `expo-camera`): один скан — ребёнок принят или отдан, на экране «Принято: Мария Иванова» и кто привёл. Если доступа к камере нет, сканер предлагает разрешить её или открыть настройки; кнопки в очереди работают в любом случае.

### Кто в саду

```
Посещение                             Центральный
┌─────────────────────────────────┐   ┌─────────────────────────────────┐
│  ┌──────────────┬────────────┐  │   │ ‹ Назад     Центральный         │
│  │ Кто в саду ● │   Журнал   │  │   │                                 │
│  └──────────────┴────────────┘  │   │  В саду 23 из 40                │
│                                 │   │                                 │
│  В саду 31 ребёнок              │   │  РОМАШКА · 15 ИЗ 18             │
│  ┌───────────────────────────┐  │   │  ● Мария Иванова                │
│  │ Северный      8 из 20   › │  │   │  ● Пётр Смирнов                 │
│  │ 2 группы                  │  │   │  …                              │
│  │ Центральный  23 из 40   › │  │   │  СОЛНЫШКО · 8 ИЗ 15             │
│  │ 3 группы                  │  │   │  …                              │
│  │ Без группы            1 › │  │   │  ЗАЙЧИК · 0 ИЗ 7                │
│  └───────────────────────────┘  │   │  Сейчас никого нет              │
└─────────────────────────────────┘   └─────────────────────────────────┘
```

- Сначала выбор филиала: у каждого «в саду / всего детей в группах» и число групп. Нажатие открывает филиал, где дети разбиты по группам, у группы — «сейчас / всего». Группы без детей тоже показываются — «Новая» и под ней «Детей пока нет»: иначе администратор не найдёт только что созданную группу.
- Если филиал один и все дети в группах, выбора нет: группы сразу на вкладке.
- **«Без группы»** — отдельной строкой в конце списка филиалов. Это дети в саду, которые не состоят ни в одной группе: без группы у ребёнка нет и филиала, поэтому их нельзя показать внутри филиала.
- **«Другие группы»** — если у группы филиал, которого нет в `GET /branch/list` (например, закрыт). Так ни один ребёнок в саду не пропадёт из подсчёта.
- **Изменить** у заголовка каждой группы — только у администратора (у сотрудника ссылки нет). Открывает «Состав группы» (см. ниже): добавить, перевести и убрать детей.
- Обновление: потянуть вниз и при каждом возврате на вкладку или на экран филиала, как на «Мои дети».
- Нажатие на ребёнка откроет его карточку, когда она появится.
- **API:** один запрос `GET /group/presence` без фильтра (все активные группы с `branch_external_key`, `total_children`, `present`, плюс `without_group` и `total_present`) и `GET /branch/list` для названий. Разбивка по филиалам — на клиенте: так одним запросом известны счётчики всех филиалов для экрана выбора, а экран филиала открывается без загрузки. Фильтр `branch_external_key` у `/group/presence` не используем: он всё равно не отделяет детей без группы, `without_group` приходит одинаковым при любом филиале.

### Состав группы

```
┌─────────────────────────────────────┐
│  Состав группы              Готово  │
│  «Солнышко» · Центральный           │
│  🔍 Фамилия, имя                    │
│  ┌──────────┬────────────┬────────┐ │
│  │В группе ●│ Без группы │Все дети│ │
│  └──────────┴────────────┴────────┘ │
│  Иванова Мария          [ Убрать ]  │
│  Солнышко · 4 года                  │
│  Смирнов Пётр           [ Убрать ]  │
│  Солнышко · 5 лет                   │
└─────────────────────────────────────┘
```

- Модальный экран из «Посещения» по ссылке «Изменить» у группы и из «Сада» (`components/group-members-screen.tsx`, маршруты `visits/group-members.tsx` и `garden/group-members.tsx` — в стеке своей вкладки). Группа с детьми открывается на «В группе», пустая — сразу на «Без группы»: новую группу обычно заполняют ими. «Все дети» — чтобы перевести ребёнка из другой группы.
- **Ребёнок состоит в одной группе.** Нажатие на ребёнка без группы добавляет его сразу. Если он в другой группе — подтверждение «Перевести в „Солнышко“? Иванова Мария сейчас в группе „Ромашка“».
- **Убрать из группы — только с подтверждением**, чтобы нельзя было сделать это случайно:
  - строка ребёнка группы не нажимается, убрать можно только отдельной красной кнопкой «Убрать»;
  - затем диалог «Убрать из группы „Солнышко“?» с объяснением, что ребёнок останется без группы, кнопки «Отмена» и «Убрать» (destructive). Запрос уходит только после «Убрать»;
  - ребёнок остаётся в списке с «Без группы» и «＋» — если убрали по ошибке, вернуть можно одним нажатием.
- Экран не закрывается после изменений, можно менять следующего. Закрыть — «Готово» или свайп вниз.
- Ошибка — красным под именем ребёнка («Не удалось добавить. Повторить», «Не удалось убрать из группы. Повторить», «Ребёнок или группа удалены. Обновите список»).
- Создать нового ребёнка отсюда пока нельзя — ждёт «Нового ребёнка» во вкладке «Люди».
- **API:** дети — `GET /user/people?category=CHILD` с `group_external_key` («В группе»), `without_group=true` («Без группы») или без фильтра, поиск `q`, страницы. Изменения — только администратор (`USER_WRITE`):
  - `PUT /group/{key}/children/{child_key}` — добавляет в группу, в том числе пустую, из прежней группы переводит, повтор ничего не меняет; 404 — группа или ребёнок удалены, 400 — не ребёнок;
  - `DELETE /group/{key}/children/{child_key}` — убирает из группы, 204; если ребёнка в группе уже нет (например, его перевели, пока админ подтверждал), ничего не меняет. Запись о составе удаляется, а не помечается `DELETED`: уникальный индекс `(группа, пользователь, статус)` не дал бы убрать ребёнка из той же группы второй раз.
  - После изменения приложение перечитывает «Кто в саду» и, если открывался, список «Людей».

- **День → группа → ребёнок.** Дни — новые сверху. Внутри дня — группы по названию, «Без группы» в конце; в заголовке группы — сколько детей из неё было в этот день (и филиал, если филиалов несколько). В группе — по строке на ребёнка, по имени.

Без глаголов «привела / забрал»: пол представителя сервер не отдаёт.

- Подгрузка страницами по 100 отметок при прокрутке (`onEndReached`), обновление — потянуть вниз.
- Потом: фильтры по дате и группе, переход в карточку ребёнка, «Вся история» из карточки.
- **API:** `GET /visit/list?sortBy=created&sortOrder=DESC` — лента всего сада страницами, с ФИО ребёнка и представителя, временем и с 29.09.2026 — `group` (нынешняя группа ребёнка: `external_key`, `name`, `branch_external_key`, `branch_name`; нет — без группы). Разбивка по дням, группам и детям — на клиенте (`utils/journal.ts`). Время приходит без часового пояса, бэкенд пишет его в UTC — переводим в местное при показе. На старом бэкенде без `group` все дети попадают в «Без группы».

`app/(admin)/requests/`: свой стек «список → заявка», slice и saga `requests`.

- Значок с числом заявок на вкладке. Заявки грузятся сразу при входе в режим администратора и при каждом открытии вкладки.

### Кто в какой группе

| Группа | Кто попадает | Строка списка |
| --- | --- | --- |
| **Дети** | роль пользователя `VISITOR` | ● в саду / ○ нет, ФИО, группа (с филиалом, если филиалов несколько) и возраст. Ребёнок без группы — «Без группы», чтобы администратор это заметил |
| **Родители** | все, кто связан хотя бы с одним ребёнком (`child-representative` с любой ролью связи: родитель, родственник, знакомый), а также пользователи с ролью `PARENT` без детей | ФИО, кем приходится и кому: «мама: Мария, Пётр», «бабушка: Пётр». Без связей — «детей не привязано»: обычно это только что подтверждённая заявка, которую ещё не связали с ребёнком. Кнопка 📞 звонит сразу (`tel:`) |
| **Сотрудники** | роли пользователя `ADMIN` (администратор) и `EMPLOYEE` (сотрудник: воспитатель и другой персонал с доступом к приложению) | ФИО, роль словом («Администратор», «Сотрудник») и филиал, если сотрудник закреплён за ним. Кнопка 📞 |

- **Один человек может быть в двух группах.** Администратор, который водит в сад своих детей, есть и в «Сотрудниках», и в «Родителях». Карточка у него одна.
- «Родители» — название группы в интерфейсе, хотя в ней и бабушки, и знакомые. Кем человек приходится ребёнку, видно по строке, поэтому отдельная группа «Родственники» не нужна.
- В списках только активные учётные записи. Заявки на регистрацию (`PENDING`, `REJECTED`) живут во вкладке «Заявки», удалённые после отзыва согласия (`DELETED`) не показываются нигде.
- **Отключённые** — последней строкой каждого списка, «Отключённые · 3 ›», открывают тот же список отключённых этой группы. Отдельная вкладка переключателя для них не нужна: они нужны редко, а четвёртая вкладка сделает переключатель тесным.

### Поиск и фильтры

- Одна строка поиска на все три группы. Текст сохраняется при переключении группы: «Иванова» в «Детях» и тут же в «Родителях» — частый путь «нашёл ребёнка → найди маму».
- Ищем по фамилии, имени и отчеству; в «Родителях» и «Сотрудниках» — ещё по телефону (любые цифры номера) и email. Поиск с задержкой 300 мс после ввода, пустой запрос — весь список.
- У «Детей» фильтр «Все группы ▾»: филиал → группа, плюс «Без группы». В остальных группах фильтров нет.
- Сортировка по фамилии, подгрузка страницами при прокрутке, обновление — потянуть вниз.
- Переключатель помнит последнюю группу, пока открыта вкладка. При первом открытии — «Дети».

**Сделано 28.09.2026 в `visit-control-service`:** `GET /user/people` (`PeopleController`, `PeopleServiceImpl`), только для `USER_WRITE`. На стенд ещё не выложено.

`GET /user/people?category=CHILD|PARENT|STAFF&q=&group_external_key=&without_group=&page=0&size=30`

- **Страницы** — стандартный `Page` Spring (`content`, `totalElements`, `number`, `last`), по умолчанию 30, максимум 100. Фильтры, поиск и сортировка (фамилия, имя, отчество) считаются в базе, поэтому `totalElements` честный — это «124 ребёнка» в шапке. Приложение подгружает следующие страницы при прокрутке.
- **Кто в какой категории:** `CHILD` — роль `VISITOR`; `STAFF` — `ADMIN` и `EMPLOYEE`; `PARENT` — роль `PARENT` или хотя бы одна активная связь с активным ребёнком (любая роль связи). Сотрудник с детьми приходит и в `STAFF`, и в `PARENT`. Всегда только `ACTIVE`: заявки и удалённые не попадают.
- **Поиск `q`:** каждое слово должно найтись в фамилии, имени, отчестве или email; если в слове не меньше трёх цифр — ещё и в цифрах телефона («912345» найдёт `+79123456789`, «1311» — `89131112233`). Регистр не важен, `%` и `_` экранируются.
- **Фильтры детей:** `group_external_key` — дети группы, `without_group=true` — дети без группы.
- **Ошибки:** `size` больше 100, отрицательный `page`, `q` длиннее 100 — 400 `VALIDATION` с именем параметра; неизвестная `category` — 400.

| Поле ответа | У кого | Что это |
| --- | --- | --- |
| `external_key`, `surname`, `first_name`, `patronymic`, `role`, `gender`, `birth_date`, `phone`, `email` | все | строка списка, кнопка 📞; `role` — роль пользователя (`ADMIN`, `EMPLOYEE`, `PARENT`, `VISITOR`) |
| `group`: `external_key`, `name`, `branch_external_key`, `branch_name`; `null` — не в группе | дети | «Солнышко · Центральный» или «Без группы». Если групп несколько — первая по названию |
| `present` | дети | ● в саду: последняя отметка — «пришёл» |
| `children`: `external_key`, `first_name`, `surname`, `link_role` (`PARENT`, `RELATIVE`, `ACQUAINTANCE`); пустой список — детей не привязано | родители | «мама: Мария, Пётр», «бабушка: Пётр». Удалённые дети не показываются |

Поля, которые к категории не относятся, в ответе отсутствуют. Группы, связи и «в саду» сервер добирает одним запросом на страницу, а не на каждого человека.

**Пока нет:** `status=BLOCKED` и счётчика «Отключённые · 3» — появятся вместе с обратимым отключением (раздел «Отключение детей и родителей»); филиала у сотрудника — сотрудники пока ни к какому филиалу не привязаны.

Проверено на временном Postgres: категории, сотрудник-родитель в двух списках, исключение заявок и удалённых, поиск по ФИО и цифрам телефона, фильтры по группе, страницы, 400 на неверные параметры, 403 для сотрудника и родителя.

### Новый ребёнок

Одна форма из трёх блоков, поля и проверки — как в регистрации (`form-field`, маска даты, переключатель пола):

1. **О ребёнке:** фамилия, имя, отчество (или «Нет отчества»), дата рождения, пол. Email и телефона у ребёнка нет.
2. **Группа:** выбор филиала и группы. Можно пропустить.
3. **Представители:** «＋ Добавить» → поиск взрослого → выбор роли связи (родитель, родственник, знакомый). Можно пропустить.

Сохранение: `POST /user` с ролью `VISITOR` → затем добавление в группу → затем `POST /child-representative` на каждого представителя. Если упал второй или третий шаг, ребёнок уже создан. Тогда экран открывает его карточку с сообщением «Ребёнок создан, но не удалось добавить: …», а не показывает ошибку всей формы. Иначе повторное нажатие «Сохранить» создаст второго ребёнка.

**Нужен бэкенд**: `POST /user` принимает роль по `external_key`, а список ролей получить нечем. Нужен `GET /role/list` или приём роли по имени.

### Новый взрослый

Те же поля, что в регистрации, плюс обязательный email: на него придёт пароль (`POST /user` сам генерирует и отправляет пароль). Согласие на обработку ПДн администратор за человека не даёт. Поэтому обычный путь для родителя — заявка из приложения, а ручное создание — для тех, кто не может подать заявку сам. Юридическую сторону такого варианта нужно уточнить (см. «Открытые вопросы»).

### Новый сотрудник

Поля как у нового взрослого (ФИО, дата рождения, пол, email, телефон) плюс **роль** и, если филиалов несколько, **филиал**. Пароль придёт на email, как родителю. Роль — переключатель «Сотрудник / Администратор», по умолчанию «Сотрудник». Сотрудник видит, кто в саду, и журнал; администратор — всё. Выбор «Администратор» — действие с последствиями: подтверждение «Иванова Ольга получит полный доступ ко всем данным сада».

**Нужен бэкенд:** то же, что для «Нового ребёнка» (`GET /role/list` или роль по имени), и закрепление сотрудника за филиалом, если оно нужно.

Устроена так же: контакты с кнопками «Позвонить» и «Написать» (`tel:` и `mailto:`), статус учётной записи, список его детей с ролью связи (`GET /child-representative/children`), история согласий на обработку ПДн (`GET /user/{key}/consents`).

## Связь ребёнка и представителя

Связь создаётся с двух сторон: из карточки ребёнка («＋ Добавить представителя») и из карточки родителя («＋ Добавить ребёнка»). В обоих случаях поиск человека, затем выбор роли связи:

| Роль связи | Подпись в интерфейсе | Что может представитель |
| --- | --- | --- |
| `PARENT` | родитель | видит ребёнка, отмечает приход и уход |
| `RELATIVE` | родственник | то же |
| `ACQUAINTANCE` | знакомый (няня, сосед) | то же. Ограничивать ли его, пока не решено (открытый вопрос в `children-screen.md`) |

`POST /child-representative` и `DELETE /child-representative` уже есть. Повторная связь даёт 409, приложение показывает «Этот человек уже привязан к ребёнку».

## Отключение детей и родителей

Отключение, а не удаление: ребёнок выбыл из сада, родитель больше не должен забирать ребёнка. История посещений при этом остаётся.

- **Ребёнок** пропадает из групп, из «Посещения» и из «Мои дети» у всех представителей. Отметить его нельзя.
- **Взрослый** не может войти, а отметки от его имени не принимаются.
- Отключённые видны в «Люди» строкой «Отключённые» в конце списка группы, в их карточке кнопка «Включить».
- Подтверждение с последствиями: «Отключить Марию Иванову? Она пропадёт из группы „Солнышко“ и у трёх представителей».

**Нужен бэкенд.** Эндпоинта нет. Статус `DELETED` для этого не подходит: так помечаются учётные записи после отзыва согласия на обработку ПДн, и такие записи не восстанавливают. Нужен отдельный обратимый статус, например `BLOCKED`, и `POST /user/{key}/block` и `/unblock`. Отдельно: JWT живёт 24 часа. Если сервер не проверяет статус пользователя при каждом запросе, отключённый родитель ещё сутки сможет отмечать детей.

## Состояния и ошибки

Общие правила для всех экранов раздела, чтобы не описывать их на каждом:

| Ситуация | Поведение |
| --- | --- |
| Загрузка списка | Спиннер по центру; при повторной загрузке список остаётся на месте, крутится `RefreshControl` |
| Пустой список | Текст по смыслу («Новых заявок нет», «В группе пока нет детей») и основное действие, если оно есть |
| Ошибка загрузки | «Не удалось загрузить данные» и «Повторить» |
| Удаление, отключение, отклонение | Всегда диалог подтверждения с названием объекта и последствиями |
| Создание и редактирование | Кнопка блокируется до ответа; без автоматических повторов, как у регистрации |
| 403 | «Недостаточно прав» — если роль сменили, пока приложение было открыто |
| 409 | Текст по коду ошибки из ответа: «Email уже занят», «Филиал не пустой», «Уже привязан» |

## Реализация в приложении


После входа `auth.tsx` выбирает маршрут по `user.role` вместо безусловного `/children`.

**Данные.** В разделе администратора около 25 запросов, и почти все — чтение списков и запись с последующим обновлением этих списков. Если писать для каждого slice, saga и флаги загрузки, как в `registration` и `children`, получится несколько тысяч строк однотипного кода. Предлагаю для этого раздела RTK Query: он уже входит в `@reduxjs/toolkit`, новых зависимостей не нужно. Поверх текущего `visitControlApi` он работает через свой `baseQuery`, так что Bearer, 401 и ретраи остаются общими. Он кэширует ответы, считает `isLoading` и `isFetching` и после изменений сам перечитывает затронутые списки через теги (`invalidatesTags: ['Branch']`). Для «Мои дети» saga остаётся: там особая логика проверки статуса перед отметкой.

Это отступление от паттерна в `memory-bank/systemPatterns.md`. Если решим так делать, его нужно дописать туда.

## Порядок работ

1. **Каркас и то, что работает на текущем API:** выбор экрана по роли, вкладки, «Заявки» целиком, филиалы (список, создание, переименование, удаление), список групп филиала, «Посещение»: «Кто в саду» плоским списком и «Журнал» без фильтров, карточка родителя со связями и сбросом пароля.
2. **«Люди» на `GET /user/people`** (бэкенд готов): три группы, поиск, фильтр по группе, строки со связями и группами.
3. **После ролей и `GET /user/{key}`:** создание детей, взрослых и сотрудников, связи, карточки.
4. **После API групп:** управление группами, состав группы, «Родители» и «В саду» в группе, «Посещение» по группам.
5. **После обратимого отключения:** отключение и включение детей и взрослых.

## Открытые вопросы

- Нужен ли администратору весь этот функционал в телефоне, или часть (создание филиалов, массовое заведение детей в начале года) удобнее в веб-админке? - **Кто считается сотрудником** в «Люди → Сотрудники»: только те, кто входит в приложение (администраторы, будущие воспитатели), или весь персонал сада, включая тех, у кого нет учётной записи (повар, медсестра)? От ответа зависит, нужен ли сотрудник без email и пароля.
