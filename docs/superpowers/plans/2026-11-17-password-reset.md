# Восстановление пароля в ДоброВходе

17.11.2026 · Технический план для Expo-приложения и установленной PWA.

Пользователь открывает «Забыли пароль?» на экране входа, получает шестизначный код по email, задаёт новый пароль и проходит обычную настройку сессии. Смена известного пароля в профиле входит в объём работ, потому что после неё клиенту понадобится заменить токен. Письмо на девятом макете проверяем при интеграции с сервером.

## Исходная база

- `feat/password-reset` создана от актуального `origin/master` (`85cfb7a`). Существующий checkout `develop` содержит локальные изменения, upstream удалён.
- В артефакте PWA 1.0.8 указан `e42f13f` из `origin/fix/session-validation-budget`. Эта история разошлась с `master`. В release-ветке есть manifest, service worker, исправления темы, API URL, профиля и восстановления сессии. Текущая версия на рабочем домене по артефакту не устанавливается.
- Контракт описан в приложенном `password-reset.md`. В полученных ветках GitHub бэкенда `origin/main` и `origin/develop` реализацию и упомянутый OpenAPI не нашла. GitLab не прошёл проверку SSH-ключа хоста. Для интеграции нужен коммит или OpenAPI развёртываемой версии.

## 1. Дизайн-система и UI Kit

1. Сделать явную точку входа для общих компонентов приложения, например `components/ui/index.ts`, и описать правила применения в `docs/design-system/`. Использовать текущие `constants/palette.ts`, `usePalette` и `makeStyles`. Формализовать отступы, радиусы, типографику, контуры и состояния, которые нужны экранам входа. Сохранить существующую палитру и темы.
2. Включить в UI Kit текущие `FormField` и `PasswordField`, сохранив их API и совместимость с регистрацией и профилем. Переиспользовать текущие стили формы для общей карточки, кнопки, текстового действия и сообщения о состоянии. Разметку страницы и навигацию оставить в auth-экранах и Expo Router. Ввести общий компонент сегментированного ввода кода на основе одного доступного поля. PIN-клавиатуру сохранить в существующем сценарии.
3. Добавить dev-only каталог внутри приложения для native и web. Использовать вымышленные значения. Показать обе темы, узкую ширину, long text, фокус, ошибки, загрузку, disabled и успех. Проверить отсутствие каталога в доступной навигации release-сборки. Принять внешний вид на входе и в форме пароля профиля. Эти два экрана станут первыми реальными потребителями UI Kit.
4. До реализации восстановления снять текущий экран входа и согласовать два варианта композиции ключевых экранов в существующей теме. Сохранить композицию референсов с короткой шапкой, карточкой формы, шестью видимыми ячейками, отдельным блоком «Письма нет?» и экраном успеха. Системные клавиатура и статус-бар остаются системными.

**Приёмка этапа** — вход и профиль пользуются общими компонентами, сохраняют сценарии и выглядят предсказуемо в обеих темах. Каталог открывается в dev-сборке Expo и web.

## 2. Общая база native и PWA

- Сверить deployed revision PWA с release-артефактом и разницу с `master`. Интегрировать актуальные PWA-изменения в ветку задачи отдельным диффом. Проверить web-хранилище сессии, тему, API URL, манифест, service worker и обновление с установленного релиза. Убедиться, что PIN и обычный вход работают на обеих сборках перед подключением нового сценария.
- Для PWA использовать существующий same-origin `/api` и fallback навигации. Проверить прямой переход и перезагрузку на каждом новом маршруте, отсутствие кэширования ответов reset API и доступность `Retry-After`. Если целевой стенд использует cross-origin API, проверить экспонирование заголовка в CORS.
- Этот шаг можно начать одновременно с UI Kit. Перед разработкой reset-маршрутов нужен единый рабочий исходник обеих сборок.

## 3. Контракт и состояние восстановления

Добавить типизированные методы в `services/api/visit-control-api.ts`. Вызовы публичные, без bearer и автоматического повтора POST. Вызовы и ошибки исключить из логирования payload. Из ошибок извлекать только необходимые поля. Проверить имя и вложенность `attempts_left` и `Retry-After` по OpenAPI и на стенде.

| Вызов | Успех | Обработка ответа |
| --- | --- | --- |
| `POST /password/reset/request` с `email` | `resend_after_sec`, `code_ttl_sec` | `400 VALIDATION` у поля, `429` с отсчётом из заголовка |
| `POST /password/reset/verify` с `email`, `code` | `reset_token`, `expires_in_sec` | `400 RESET_CODE_INVALID` с остатком попыток, `410` с перезапросом кода, `400 VALIDATION`, `429` |
| `POST /password/reset/confirm` с `reset_token`, `new_password` | `access_token` | `400 VALIDATION` сохраняет доступ к форме, `410` возвращает к получению кода. Остальные ошибки по проверенному контракту |

- Зарегистрировать публичные маршруты в `components/session/session-gate.tsx`. Добавить reset layout с состоянием в памяти на время сценария. Код, пароль и reset token держать вне Redux actions, DevTools, URL, persistent storage и телеметрии. Email передавать из входа через память. При прямом входе без состояния или после reload возвращать на ввод email.
- Хранить сроки абсолютными отметками из серверных TTL. Пересчитывать их при возврате из почты, сна или фонового режима. Для `429` учитывать заголовок; если он отсутствует, показывать «Попробуйте позже» без выдуманного срока.
- Блокировать параллельную отправку с одного экрана. При уходе, смене email и переходе к новому запросу игнорировать ответы предыдущего шага. При неопределённом результате verify дать запросить новый код, при неопределённом результате confirm — вернуться ко входу с новым паролем или начать восстановление заново.

## 4. Экраны и вход после сброса

1. **Вход и email.** Добавить действие справа под паролем в `app/auth.tsx`. Вынести проверку email из формы входа и переиспользовать её. После любого успешного request показывать одинаковый экран кода и условную подсказку о доставке. Отправку по неизвестному адресу отдельно в UI не обозначать.
2. **Код и повтор.** Ввод с цифровой клавиатурой, вставка всех шести цифр, в том числе скопированных с пробелом внутри. Подключить подсказку автозаполнения, приёмку провести на устройствах. По ТЗ отправлять при шестой цифре. Предлагаю сохранить кнопку «Продолжить» из макета для ручной отправки или повтора после сетевой ошибки. Кнопка и автосабмит вызывают одну функцию. При неверном коде показать остаток попыток, очистить поле через секунду и вернуть фокус. При `410` открыть повторный запрос с тем же email, при смене email вернуться к форме.
3. **Новый пароль.** Использовать два `PasswordField`, общую политику длины 8–72 по проверенному контракту и проверку совпадения. После verify код погашен, поэтому «Назад» ведёт на ввод email. Очистить поля и reset token при выходе из шага. Текст о завершении других сеансов включать вместе с серверным отзывом.
4. **Готово.** После confirm показать «Пароль изменён». По «Продолжить» передать access token в общий путь завершения входа, выделенный из `store/sagas/auth.ts`. Он устанавливает токен и вызывает `protectedSessionRepository.beginSession`. Дальше работают текущие PIN и настройка биометрии для соответствующей платформы. Удалить recovery из истории после перехода. При ошибке хранилища оставить возможность войти новым паролем.

## 5. Смена пароля в профиле и отзыв сессий

- `changePassword` сейчас возвращает `void`. Принять `access_token` из `PATCH /user/password` и поддержать прежний успешный ответ без токена на переходный период. Заменять JWT и в памяти, и в сохранённой записи через сериализованное обновление сессии с сохранением PIN и биометрии. Проверить выход во время запроса, ошибку записи и запоздалый 401 от прежнего токена. При подтверждённой смене и невозможности сохранить токен дать пользователю войти заново.
- Использовать текущий обработчик 401 и `notice`. Если сервер сообщает только общий 401, показывать нейтральное «Сеанс завершён. Войдите снова». Текст «Пароль изменён» использовать, когда контракт позволяет определить причину.

## 6. Проверки и выпуск

- После реализации покрыть контракт, переходы и таймеры в Jest, включая двойное нажатие, вставку, возврат из фона, просроченный токен, 429 и смену email. Добавить регрессии PIN/биометрии, PATCH с новым токеном и без него, 401 до и после ротации. Запустить `npm run test:ci`, `npm run typecheck`, `npm run lint` и сборку Expo для web.
- Визуально пройти весь сценарий на iOS, Android и установленной PWA. Проверить обе темы, ширины 320/375 px и широкую PWA, системную клавиатуру, Tab/Shift+Tab, экранный диктор, перенос длинного email, focus, loading, disabled, ошибку, успех. Автозаполнение проверить на реальном устройстве; ручной ввод и вставка должны работать везде.
- На стенде проверить доставку обоих писем, вход с новым паролем, отсутствие различий на шаге запроса между активным и неизвестным email, профиль и две параллельные сессии. Для выпуска сначала развернуть API и почту с отзывом выключенным. Затем выпустить клиенты и проверить обновление установленной PWA. После проверки совместимости включить отзыв и проверить новый и старый токены. Учитывать смены пароля, совершённые между выкладкой API и включением отзыва: по ТЗ `password_changed_at` пишется уже при выключенном флаге.
